# Agent 文件撰寫規範

本 Skill 用於判斷規則應寫入哪一層、文件應保留多少資訊，以及如何讓下一個 Agent 能夠依文件完成工作與驗收。

## 兩種預算

- **Context load 預算**：讀者為了重建任務所需載入的事實、限制、檔案位置與交叉引用。刪除重複敘述，保留會改變決策或執行順序的資訊。
- **Cognitive load 預算**：讀者在同一時間需要記住的概念、例外與依賴關係。以段落、表格或清單分組，每個區塊只處理一個主要判斷。

Context load 過高會讓必要資訊被淹沒。Cognitive load 過高會讓讀者需要自行拼接規則。編寫文件時，同時檢查兩種預算。

## 資訊階梯與 Progressive Disclosure

文件內容依下列三層排列：

1. **結果層**：先說明目標、決策或完成條件。
2. **規則層**：列出會改變執行方式的限制、輸入、輸出與失敗處理。
3. **證據層**：提供範例、例外、指令、檔案路徑或驗證結果。

使用 Progressive Disclosure 時，先提供結果層與規則層。只有在下列 branch test 成立時，才加入證據層或連結至證據層：

- 讀者無法依結果層與規則層判定是否完成。
- 例外情境會改變執行路徑或驗收結果。
- 下一階段需要精確檔名、指令或格式才能機械執行。

僅用來補充背景、沒有改變決策或驗收方式的內容不進入主要流程，可放在連結目標或參考區段。

## Completion Criterion

完成條件必須同時具備兩種性質：

- **Clarity**：觀察者能從檔案、命令輸出或測試結果判定通過或失敗，不需要猜測「完成」的意思。
- **Demand**：條件直接對應需求中的結果、範圍或限制，沒有以形式上的檔案存在取代實際行為。

例如，新增 API 的完成條件應同時描述端點行為與可驗證的回應結果。只描述「建立 Controller」只有形式上的 Clarity，沒有覆蓋 Demand。

## Leading Word

清單項目、步驟與驗證條件以能表達判斷的 leading word 開頭，例如「建立」「讀取」「確認」「拒絕」「保留」「刪除」或「輸出」。Leading word 讓讀者先知道該項目的動作或狀態，再讀取細節。

## Negation 反模式

新增規則優先使用正面陳述，直接說明應採取的行為。只有讀者確實可能採取錯誤方向，且刪除否定前件會造成誤解時，才保留否定句。

既有 Crucial 級禁令不因本 Skill 追溯改寫。改寫既有文件時，不把原本的寫法當作正文中的對照對象。

## No-op 檢測

逐句檢查下列問題：

- 刪除後，模型的選擇、執行順序、輸入輸出或失敗處理是否改變？
- 句子是否只重述工具已提供的行為或目錄實際狀態？
- 句子是否與同一文件或更高優先權規則重複？

若三項答案都是否定，該句子屬 no-op，可刪除。大幅改版時，將被刪除的規則與判定理由記錄在差異報告，避免靜默遺漏原始條目。

## 環境即 Source of Truth

需要精確事實時，優先讀取實際檔案、設定、命令輸出或測試結果。文件只保留執行所需的判斷與引用位置，不複製可能過期的環境摘要。

引用環境資料時，至少指出來源路徑、命令或驗證方式。來源不存在、格式不符或輸出不足以判定時，將其列為待確認條件，不以推測填補。

## 寫作檢查清單

- 先寫結果層，再寫會改變執行的規則。
- 為每個完成條件檢查 Clarity 與 Demand。
- 為每個新增清單項目選擇明確的 leading word。
- 對新增否定句執行誤解風險檢查。
- 對大幅改版保留刪除項目的差異理由。
- 以實際環境作為事實來源，避免複製可過期的狀態描述。
