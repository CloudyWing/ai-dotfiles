# 技術內容事實校閱

對使用者提供的技術文件、筆記或說明進行逐條查核，標記可能有誤或已過時的資訊。

## 校閱範圍

### 1. 觀念正確性

- 技術定義是否正確（如「同步」與「非同步」的說明、「堆疊」與「堆積」的區分）？
- 比較說明是否有邏輯矛盾（如「A 比 B 快，B 比 C 快，C 比 A 快」）？

### 2. 術語一致性

- 同一概念是否在文件中使用了多個不同名稱但未說明對應關係？
- 術語是否符合該技術領域的慣用說法（如 .NET 慣用「例外」而非「異常」）？

### 3. API / 版本正確性

- 提到的方法名稱、屬性名稱是否存在於宣稱的版本中？
- 是否引用了已廢棄 (deprecated) 或已移除的 API？
- 版本號與功能的對應是否正確（如某功能從哪個版本開始支援）？

### 4. 命令與路徑

- 文件中的 CLI 指令是否有明顯的語法錯誤？
- 範例路徑是否符合目標平台慣例（如 Windows vs Unix）？

## 強制聯網查證規則

遇到以下情境時，**必須優先使用 Web Search 工具查閱官方文件或版本發布說明**，不得僅依賴訓練資料作答：

- 文件中提及特定版本號的 API 行為或功能（如「.NET 8 起支援...」）。
- 文件中引用了可能在近期版本中異動的方法、屬性或套件。
- AI 對某項說法「不確定但有印象」，無法明確說出文件來源。
- 文件內容與 AI 訓練資料中的認知有出入，但無法確定哪方正確。

Web Search 後，將查詢到的官方文件連結作為「依據」填入輸出的 `❌ 有誤` 或 `⚠️ 待確認` 欄位。若 Web Search 後仍無法確認，維持 `⚠️ 待確認` 標記，說明已查詢但無法找到明確依據。

## 輸出格式

逐條列出問題，格式如下：

```markdown
## 校閱結果

### ✅ 無需修正
[若全部正確，此處說明]

### ⚠️ 待確認（AI 無法 100% 確認，需查閱官方文件）
- **第 X 段**：「...原文引用...」
  可能問題：[說明疑慮]
  建議查閱：[對應的官方文件或規格來源]

### ❌ 有誤（有明確依據）
- **第 X 段**：「...原文引用...」
  問題：[具體說明錯誤之處]
  正確說法：[修正後的表述]
  依據：[來源或推理依據]
```

## 重要限制

- **不修改原文**：此 Skill 僅產出報告，不直接更改文件內容。
- **誠實標示不確定性**：若 AI 訓練資料無法確認某項說法（特別是版本細節或近期 API 異動），必須標示為「⚠️ 待確認」而非給出貌似正確的答案。
- **不補充「最新資訊」**：若原文說法有時效性疑慮，僅標記並提示使用者查閱，不依訓練資料自行補充最新資訊。
- **校閱完成後，回問使用者確認**：輸出校閱報告後，詢問使用者「以上校閱結果是否正確？確認後我可以直接修改文件。」若使用者確認，則：
  - 若原始內容來自**具體檔案路徑**：直接使用 Edit 工具修正文件中的有誤段落，保留其他未標記內容。
  - 若原始內容來自**對話貼入（無具體路徑）**：輸出完整修訂稿，供使用者手動替換。
