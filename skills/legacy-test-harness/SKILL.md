# 外部測試專案評估與結果判讀

## 範圍與邊界

本 Skill 指引在原專案之外建立測試專案，以單元或元件粒度驗證商業邏輯，降低修改一處後造成其他行為回歸的風險。採盡力而為原則，依可驗證的行為選擇可行測試層級。測試數量與程式碼覆蓋率不作為驗收條件。

HTTP、UI 與資料庫的黑箱整合測試分別交由 [csharp-integration-test](../csharp-integration-test/SKILL.md)、[api-smoke](../api-smoke/SKILL.md) 與 [browser-smoke](../browser-smoke/SKILL.md)。單元測試的 NUnit 寫法參照 [csharp-nunit](../csharp-nunit/SKILL.md)。

評估階段只讀取核准範圍內的原專案檔案，不修改原專案，也不安裝或還原套件。測試專案建立在原專案 Repository 之外，可使用獨立 Repository 或本機目錄。需要安裝或還原套件時，先交由協調者取得當輪授權。

## 評估與測試計畫

1. 選取與近期修改直接相關、近期常被修改，或容易連帶影響其他行為的候選標的。記錄每個標的的選取理由，不進行無目的的全庫盤點。
2. 讀取候選標的及其必要相依，記錄靜態成員、`HttpContext`、組態、時間、資料存取與外部服務等相依情形。
3. 依測試可行性將每個標的歸入下表其中一類，並記錄分類理由、預期驗證方式與限制。

| 分類 | 判定方式 | 測試計畫內容 |
| --- | --- | --- |
| 直接可測 | 行為可由公開方法、輸入與輸出觀察，或可用記憶體資料驗證 | 記錄案例、輸入資料、獨立確認的預期結果與測試層級 |
| 可用替換技術切斷 | 相依可在外部測試專案中替換，且替換後仍能驗證目標行為 | 記錄相依、替換技術、必要條件、替換後未涵蓋的行為與退場條件 |
| 交給整合測試 Skill | 驗證需要真實資料庫、HTTP、UI 或其黑箱互動 | 指定對應的整合測試 Skill，記錄本測試計畫不驗證的行為 |

測試計畫應保留候選標的、選取理由、相依分類、引用方式、替換方式、預期值來源與確認狀態，以及未覆蓋項目與原因。每個標的都要有分類與理由。

## 外部測試專案與原專案保護

1. 將測試專案放在原 Repository 之外，並依被測程式的 .NET 版本選擇相容的 Target Framework 與 Runner。
2. 依版本同步需求、建置條件與來源可用性，選擇 `ProjectReference` 或建置後的 DLL。測試計畫需記錄所選引用方式與被測版本識別資料。
3. 保持原專案版控內所有追蹤檔案不變，範圍包含原始碼、`.csproj`、`.sln` 與設定檔。原專案目錄中只允許建置產生的 `bin`、`obj` 輸出。
4. 使用 `InternalsVisibleTo`、修改原專案 Interface、加入 Adapter，或其他要求修改原專案的做法時，停止該標的的測試規劃，記錄為未覆蓋與原因。
5. 以原專案的 `git status --porcelain --untracked-files=all`、`git diff HEAD --` 與 `git diff --cached --` 留存狀態證據。追蹤檔案有任何變更，或 `bin`、`obj` 以外出現新檔時，原專案保護檢查不通過。

## 相依替換技術

替換方式依相依特性與驗證價值選擇。每種方式需記錄適用條件、限制與停止使用的條件。

| 相依情形 | 可選方式 | 限制與退場條件 |
| --- | --- | --- |
| Interface 或 `virtual` 成員 | 使用 NSubstitute 建立替身並設定呼叫結果或驗證互動 | 替身只證明測試設定下的呼叫與結果，不能取代真實資料庫或 HTTP 行為。若目標行為依賴 Provider 語意，轉交整合測試 Skill |
| 非 public 成員 | 優先由公開行為驗證。公開行為無法觀察目標結果且該結果有明確驗收價值時，才以反射測試指定成員 | 反射會綁定內部名稱與實作。設定成本或維護成本高於驗證價值時，停止使用並記錄未覆蓋與原因 |
| 靜態、sealed 或非 virtual 成員 | 可評估 Harmony 或 Microsoft Fakes 執行期替換。Microsoft Fakes 需要 Visual Studio Enterprise | 這些技術為選用方式。先確認工具、授權、Runner 與版本相容性；成本過高或環境不符時跳過並記錄未覆蓋與原因，不判定為失敗 |
| 需要真實資料庫或 HTTP 的行為 | 使用對應整合測試 Skill | 不以記憶體替身宣稱已驗證資料庫 Provider、HTTP 協定或遠端服務行為 |

不得為了測試而要求原專案新增測試接縫、改變公開介面或設定 `InternalsVisibleTo`。替換技術無法在原專案外切斷相依時，保留未覆蓋紀錄，或將案例交給適用的整合測試 Skill。

## 預期值與案例狀態

每個案例將預期值標記為下列其中一種，並記錄預期值來源、確認者、確認狀態與確認日期。

| 預期值類型 | 來源 | 確認方式 |
| --- | --- | --- |
| 既有相容行為 | 已存在的程式行為、文件或既有測試 | 由協調者取得有權確認者的確認，再建立可作為通過依據的基準 |
| 業務需求 | 已確認的需求或業務規則 | 由需求或業務規則的負責者確認預期結果 |

未經確認的預期值標記為「待釐清」，該案例不得計入通過。單次觀察到的程式輸出只作為證據，不自動成為預期值或新的通過基準。確認前不以測試結果推定業務語意。

## 結果契約與假綠燈判定

每次執行至少記錄命令、案例統計、Exit Code、耗時、Runner 與套件版本、被測程式版本、DLL SHA-256 與測試專案版本。案例統計分別列出通過、失敗、略過、未執行與待釐清數量。

Exit Code 為 `0` 時仍須檢查各案例結果與統計。依下列條件判讀結果：

| 狀況 | 結果判定 |
| --- | --- |
| 案例數為零 | 不通過，記錄零案例 |
| 全數案例略過 | 不通過，記錄全數略過 |
| 存在未確認的預期值 | 不通過；相關案例保留為待釐清 |
| 結果契約必要欄位缺漏，包括命令、案例統計、Exit Code、耗時、Runner 與套件版本、被測程式版本、DLL SHA-256 或測試專案版本 | 不通過；列出缺少的欄位，並將結果標記為待釐清 |
| 工具或環境阻塞測試執行 | 不通過；記錄阻塞項目與原始錯誤 |
| 任一案例失敗 | 不通過；列出失敗案例與錯誤摘要 |
| 至少一個已確認案例通過，且上述阻擋條件皆不存在，且結果契約必要欄位齊備 | 可依案例結果判定通過，並保留完整統計與版本資料 |

「未執行」與「待釐清」是獨立統計項目，不合併為略過。每個未覆蓋或未執行案例都記錄原因，供後續判斷是否補測。

## 版本識別

將每次結果連結到實際被測版本與測試環境，至少記錄：

- 被測原專案的 Commit SHA，以及工作樹變更指紋；無法產生整體指紋時，列出變更檔案與各檔案雜湊。
- 被引用 DLL 的 SHA-256。使用 `ProjectReference` 時記錄實際載入的 DLL 雜湊。
- 外部測試專案版本、Target Framework、Runner 與測試套件版本。
- 執行命令、Exit Code 與耗時。

缺少被測版本、必要檔案指紋、DLL 雜湊、測試專案版本、Runner 或套件版本時，結果標記為待釐清，不判定通過。

## 失敗恢復

| 狀況 | 處置 |
| --- | --- |
| 缺少工具或套件 | 停止安裝與套件還原，記錄缺少項目及原始錯誤。由協調者取得當輪授權後處理套件；工具或套件仍不可用時標記環境阻塞，不判定通過 |
| 被測版本不明 | 停止建立基準，記錄缺少的 Commit、工作樹指紋或 DLL 雜湊。無法取得版本證據時標記待釐清 |
| 替換技術失效 | 記錄標的、替換方法與失敗原因，將案例標記為未覆蓋。保留原專案邊界，不新增原專案測試接縫或未確認的執行期替換 |
| 測試需要修改原專案 | 停止該案例，列為未覆蓋並記錄所需變更與原因。原始碼、專案檔、設定檔與 `InternalsVisibleTo` 維持不變 |
| 缺少業務預期值 | 將案例保留為待釐清，交由協調者取得確認。不得以觀察到的程式輸出自動建立基準 |

## 派遣分界

| 工作 | 執行端 | 交付內容 |
| --- | --- | --- |
| 確認需求範圍、回歸風險、預期值語意與待釐清的業務規則 | 協調者與需求或業務規則負責者 | 核准的候選標的、分類、預期值來源與確認狀態 |
| 依核准範圍讀取程式、建立外部測試專案、撰寫測試與執行已授權的驗證 | Codex 執行端 | 測試計畫、案例結果、版本識別資料及原專案 Git 狀態證據 |
| 判讀結果是否符合需求、處理預期值歧義與決定是否補測 | 協調者；業務預期值由負責者確認 | 已確認的結果判定與待處理項目 |
