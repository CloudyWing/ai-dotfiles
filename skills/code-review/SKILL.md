# 程式碼審查

對使用者提供的程式碼（或 IDE 選取範圍）進行結構化審查，輸出分層建議清單。

## 審查面向

依序從以下面向評估，有問題才列出，無問題則略過：

### 1. 正確性 (Correctness)

- 邏輯是否有明顯錯誤或邊界案例未處理？
- 例外處理是否完整？
- 非同步操作是否有競態條件 (race condition) 風險？

### 2. 安全性 (Security)

- 是否有輸入驗證缺失（SQL Injection、XSS、路徑穿越等）？
- 是否有硬編碼機密資料（API Key、密碼）？
- 是否有不安全的反序列化或動態評估？

### 3. 效能 (Performance)

- 迴圈內是否有不必要的資料庫查詢或 HTTP 呼叫（N+1 問題）？
- 是否有可以快取的重複計算？
- 集合操作是否選用了正確的資料結構？

### 4. 可讀性 (Readability)

- 命名是否清晰表達意圖？
- 方法長度是否超出單一職責範圍？
- 是否有不必要的巢狀或複雜度？

### 5. 維護性 (Maintainability)

- 是否違反 SOLID 原則（特別是單一職責、開放封閉）？
- 是否有重複邏輯應抽取為共用方法？
- 是否有魔術字串/數字未定義為常數？

### 6. 慣例符合度 (Convention)

- 是否符合 CLAUDE.md 中定義的命名慣例與格式規範？
- 是否有過時的 API 或已廢棄的寫法？

## 輸出格式

依問題嚴重程度分三級輸出：

```markdown
## 🔴 必須修正（影響正確性或安全性）
- [問題描述]：[具體位置] — [修正建議]

## 🟡 建議改善（品質與維護性）
- [問題描述]：[具體位置] — [改善方向]

## 🔵 可考慮優化（效能或慣例）
- [問題描述]：[具體位置] — [優化建議]
```

- 每個問題必須包含具體位置（行號、方法名稱或變數名稱）。
- 若各面向皆無問題，該級別直接略去，不輸出空標題。
- 審查結束後附上一句整體評語（一行）。

## 限制

- 此 Skill 僅產出建議報告，不修改任何程式碼。
- 若使用者要求修正，需明確確認後再動手。
