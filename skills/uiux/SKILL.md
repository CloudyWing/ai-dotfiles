# UI/UX 決策規範

本 Skill 依上述觸發語自動載入。自動觸發依賴模型判斷，不保證每次命中，因此當本輪工作涉及畫面或使用者可見文字而本 Skill 未被載入時，可直接以 `/uiux` 手動強制載入。

本 Skill 規範的是 UI 決策的方法與邊界，不訂定任何具體色碼、間距或字級數值。專案專屬的視覺數值由 `uiux-baseline` skill 掃描產出的樣式基準檔承載。

## 既有慣例優先

專案既有的畫面慣例優先於本 Skill 的預設作法。兩者衝突時以專案既有慣例為準，不主動將既有風格改成本 Skill 的預設。此原則對稱於 `csharp-style` skill「套用範圍」對既有 C# 專案的慣例對齊要求。

視覺數值與採用值依「基準輸入與確認狀態」核對呼叫端指定的基準及確認來源。

慣例對齊的層次高於數值對齊。畫面中的查詢條件列、資料表格、彈窗等結構，優先整段複用基準檔「常用模式範例」的骨架，其次才用原子值自行組裝。只對齊色彩與間距而重寫結構，產出的畫面仍會偏離專案既有版型。

## 基準輸入與確認狀態

內部候選版可展示待選方案；客戶展示版與實作基準版只使用已確認值；確認狀態由協調者管理。展示用途與完整版／精簡版為獨立選擇。

1. 取得呼叫端選定的 `app-name`、`baseline-path`、`sample-path`、用途及 `confirmed-choices`。單一與多 app 都需交付實際絕對路徑。`confirmed-choices` 每筆包含用途類、選定值、使用者確認來源；無待決策採用時填空清單。
2. 實讀指定基準，核對「掃描範圍」的 app-name 與 app 來源根是否符合本輪目標。`baseline-path` 須位於同一 `work-root` 的 `style-baselines` 目錄；多 app 檔名為 `ui-style-baseline.<app-name>.md`，單一 app 可沿用固定檔名。`sample-path` 須與「引用方式」記錄的樣本頁相同，並可讀取。缺欄、檔案不可讀或 app 錯配時停止並指出具體欄位與絕對缺件位置，交回協調者依 `uiux-baseline`「協調者基準準備」處理；只消費指定 app，不自行拼接路徑或換用其他基準。
3. 內部候選版逐項列用途類、全部候選與來源，標為待確認，只交協調者比較，不作下游已確認輸入。
4. 正式採用逐項對照基準的已統一慣例或 `confirmed-choices` 的使用者確認來源。已統一慣例可直接使用；本輪引用的待決策值須由協調者取得使用者確認。缺確認、契約矛盾或缺項時保留未決並停止該正式採用，回報協調者；已確認決定依既有需求摘要流程保存，不新增狀態檔或版本綁定。

## UI 線判定

需求涉及畫面時，`Analyst` 在整理需求摘要前判定本輪走哪一條線，並於回應中以單行標記宣告，格式為 `[UI 線: A]`、`[UI 線: B]` 或 `[UI 線: C]`，後接判準依據。各線的分派順序見 `workflow-orchestration` skill「需求確認後的分派」。

| 線 | 判準 | 產出 |
| --- | --- | --- |
| A | 本次變更不涉及畫面 | 依一般流程派生 `Architect`；有效深度為 `light` 時不派生 |
| B | 涉及畫面，但版面決策以文字即可描述清楚 | 派生 `Architect`，需求摘要附區塊清單與初步層級判斷；有效深度一律為 `full`（升級判定） |
| C | 需要對外溝通，或版面複雜到文字講不清 | 先派生 `Prototyper`，驗收後回填需求摘要再派生 `Architect`；有效深度一律為 `full`（升級判定） |

C 線有兩個獨立的觸發條件，任一成立即產 Demo，且需要對外展示的判準優先於下方不觸發 C 線的情境：

- 需要對外溝通，例如需求訪談、提案、對客戶展示。
- 版面複雜到文字講不清，依下方複雜度判準認定。

複雜度判準符合任一即成立：

- 單一畫面有 3 個以上並列區塊，且區塊間存在空間關係（左右分欄、主從連動）。
- 同一畫面有 5 個以上互斥狀態、分頁或步驟需要切換。
- 屬於儀表板、列表加明細、多層篩選這類版型。
- 既有畫面的版面骨架要重做，需要新舊對照才能討論。

不需對外展示且未達複雜度時，下列情境屬 B 線：

- 單欄由上而下的表單或清單頁。
- 既有畫面小幅增修。
- 只有一到兩個主要區塊的畫面。

判定為 B 線時，需求摘要須附區塊清單與初步層級判斷，供 `Architect` 產出版面資訊層級章節。判定依據不足以區分 B 與 C 時，以需求本身的溝通對象為準，需要給第三方看就走 C 線。

## 版面資訊層級決策

動任何畫面前，必須先對區塊做重要性排序，完成歸類後才決定空間配置。

### 三層歸類

| 層級 | 定義 | 配置原則 |
| --- | --- | --- |
| P0 主要動作區 | 使用者進入此畫面的主要目的所在 | 佔據進頁即見的位置與最大視覺權重 |
| P1 次要資訊區 | 支援主要目的、經常被查看但非入頁目的 | 次於 P0，仍維持可見 |
| P2 罕用收折區 | 偶爾使用的設定、進階選項、歷史紀錄 | 預設收合，需要時展開 |

### 判定依據

歸類依下列三項判斷：

- 使用者進入此畫面的主要目的是什麼。
- 各區塊的使用頻率。
- 誤操作的後果嚴重度。後果嚴重的操作不放在最容易誤觸的位置。

### 禁止事項（Crucial）

**禁止依需求清單的條列順序或 `design.md` 的敘述順序鋪排區塊。** 敘述順序反映的是撰寫順序，不是重要性。照著文件順序由上而下疊區塊，結果是每個區塊看起來一樣重要，等於沒有版面。

無法判定某區塊的層級時，列入需確認項交由使用者決定，不預設為 P1。

## 改動邊界與不可自由裁量清單

收到模糊指令（如「優化版面」「調整一下」）時，預設只動下方第一張清單的範圍。

### 可自行決定

- 區塊間距。
- 同層級內的排列順序。
- 收折與展開的預設狀態。
- 使用者可見文字的措辭，依 U1 至 U8 刪減實作手段、內部名詞、代碼與重複說明，語意不變。
- 次要元件的選用。先讀取目標 app 指定基準的「元件契約」，沿用已指定的元件、必要資源與值契約；僅對未指定的項目，在維持輸入值語意時自行選用。契約缺漏或來源矛盾時，列為需確認項並停止該項選用。

### 須先回報並取得確認

- 主色系與品牌識別，含 logo、品牌色、字體家族。
- 既有元件庫的選型與替換。
- 資訊架構的大幅調整，例如頁面拆併、導覽層級變更。
- 既有互動模式的變更，例如將既有的頁內展開改為彈窗。
- 改變錯誤訊息所指的處置動作，含合併或拆分原本對應不同處置動作的訊息。

判斷第二張清單的項目確有問題時，於決策攤開機制中列為需確認項並停止，不先斬後奏。

## 輸入控制項沿用與設計交接

日期、時間、日期時間及下拉選單依指定 app 的元件契約沿用，完成條件為元件、必要資源及值語意皆與契約相符。

1. 讀取指定基準的元件名稱、來源、代表使用點、註冊／初始化、必要 CSS、locale 與其他資源，以及顯示格式、綁定值格式、空值語意。依需求用途定位對應契約。
2. 沿用契約指定的封裝元件，連同必要資源與值契約；已指定封裝者不改成 HTML5 原生 input 或手動輸入框。原生控制項是基準慣例時沿用原生。
3. 缺少基準時交回協調者依「基準輸入與確認狀態」補件；缺特定契約、值矛盾或待決策值未確認時保留未決並停止該項設計或實作。
4. 在涉及輸入控制項的 T-code 既有需求標註後，交付以下固定元件沿用標註。contract-source 使用 baseline-path 的絕對路徑與可定位的元件契約位置。

~~~text
〔元件沿用 component=<基準元件名稱>; contract-source=<baseline-path 絕對路徑>#<元件契約定位>〕
~~~

通用到貨日期情境的格式範例如下：

~~~text
- [ ] T101 修改到貨日期欄位（C:/<專案根目錄>/src/DeliveryForm.vue）〔需求 #1〕〔元件沿用 component=SystemDatePicker; contract-source=C:/<專案根目錄>/.local/ai-sessions/style-baselines/ui-style-baseline.order.md#元件契約/日期〕
~~~

非 Workflow 計畫以相同 component 與 contract-source 記錄元件沿用，放入既有有效範圍契約的目標與驗證條件，不新增全域解析欄位。

## UI 決策攤開機制

完成畫面決策後，必須以下列固定格式輸出說明。此格式的作用是讓不具 UI/UX 背景的把關者，以業務重要性判斷版面是否合理。

```markdown
## 版面決策說明

| 區塊 | 層級 | 位置 | 理由 |
| --- | --- | --- | --- |
| ＜區塊名＞ | P0 主要動作區 | ＜位置描述＞ | ＜以業務行為陳述的理由＞ |

**本次未變更**：＜逐項列出刻意維持原樣的項目＞

**需你確認**：

| 項目 | 為何需要你決定 |
| --- | --- |
| ＜項目＞ | ＜落在不可自由裁量清單的哪一條＞ |
```

理由欄必須以業務行為陳述，例如「使用者每日進入本頁的主要目的是處理待簽核項目」。禁止以視覺詞彙陳述，例如「這樣比較平衡」「視覺動線較順」。視覺詞彙無法被非設計背景的把關者驗證，等於沒有給出理由。

「需你確認」無項目時保留標題並填「無」，不整節省略。

## 互動狀態

下列六個狀態為必備。任一畫面規劃或實作都必須交代六態的呈現方式，不得只做正常有資料的情境。

| 狀態 | 要求 |
| --- | --- |
| 載入中 | 明確的載入指示，不留空白畫面 |
| 空資料 | 須含一句成因說明與下一步動作指引，不得只留空白 |
| 錯誤 | 依使用者該採取的動作撰寫（見 U6），不並列錯誤代碼與診斷明細（見 U5） |
| 停用 | 視覺上可辨識為不可操作，並說明停用原因 |
| 提交中 | 阻擋重複提交 |
| 大量資料 | 資料遠超一屏時，所有資料仍可到達，主要動作維持可見。清單、表格與 Dialog 皆須交代捲動呈現 |

## 使用者可見文字

本章適用對象為 UI 文字與顯示給使用者的錯誤訊息，位置含 `.cs`、`.razor`、`.xaml`、`.vue`、`.ts`、`.tsx` 與資源檔。`design.md`、需求摘要與程式碼中的內部術語不直接沿用，先判定讀者再轉為使用者語言。

| ID | 規則 | 例（通用情境） |
| --- | --- | --- |
| U1 | 讀者判定：以實際使用者為準，先判定使用者是誰、能採取什麼動作。單人工具的使用者本人即維護者，不寫「聯絡開發者」 | 個人桌面工具的錯誤訊息改寫為使用者可自行採取的動作 |
| U2 | 副標與說明：只說明這頁做什麼。標題、標籤與控制項已表達清楚時不寫；不重述畫面已呈現的流程，不帶產品定位。本條只約束頁面副標與說明文字，不約束互動狀態表的空資料與錯誤文字 | 匯出頁副標重述「選擇檔案後按匯出」，整行刪除 |
| U3 | 進階參考資訊按需顯示：設定檔路徑、支援格式清單等放 Tooltip 或文件，不常駐於畫面文字 | 設定頁副標改一句用途，設定檔路徑改以 Tooltip 顯示並寫入文件 |
| U4 | 不外露內部資訊：實作手段（加密 API、儲存機制、內部流程）、內部名詞（`design.md` 與程式碼的領域內部詞）、技術名詞（更新通道名稱）、UTC 時間 | 「以 DPAPI 加密」「已建立交易快照」「UTC 時間」不出現在提醒文字 |
| U5 | 代碼只留診斷資料：錯誤代碼、失敗代碼、交易 ID 等寫入記錄或診斷資料，畫面文字不並列 | 錯誤訊息不含 `{failureCode}` |
| U6 | 錯誤依使用者該採取的動作分組：一則訊息對應一個動作（重新登入、重試、修正輸入、等待、無需處理）。需要不同動作的原因不得合併為同一則 | 「需重新登入」與「請稍後重試」各自獨立 |
| U7 | 改寫不改語意：刪減或改寫既有訊息時，訊息所指的原因與處置動作不變 | 刪除內部名詞後，訊息仍指出同一原因與同一動作 |
| U8 | 語言：介面文字語言與使用者一致，中文使用者的介面以台灣用語正體中文撰寫 | 介面不夾雜英文內部代號 |

## 響應式版面

採行動優先。先確立窄螢幕的單欄堆疊順序，依 P0、P1、P2 排序，再往上加寬。

- 斷點沿用專案既有定義。基準檔未記錄斷點時，常見三段（約 640、1024、1280）僅列為內部候選推定值，在決策攤開說明中標待確認；客戶展示版與實作基準版依「基準輸入與確認狀態」取得確認後才採用。其他基準缺項適用同一門檻。
- 表格於窄螢幕降級為卡片式呈現，或改為橫向捲動並固定關鍵欄。
- 觸控目標的最小可點擊區域不小於 44 px 見方，相鄰目標間距不小於 8 px。

## Demo 驗收

`Analyst` 驗收 `Prototyper` 產出時逐項核對下列清單，驗收程序與嚴重度映射見 `workflow-orchestration` skill「Design 與 Demo 驗收」。

| 檢查項目 | 判定依據 |
| --- | --- |
| 產品文案與設計註記分離 | 依文案用途判定，保留日期格式提示、必填錯誤、空資料引導與業務備註；設計理由、開發註記、模擬限制與待確認項只放外框或交接資料，不以「說明」「備註」字面搜尋直接否決。誤刪產品提示或畫面含設計註記為 Major；無行為影響的標點為 Minor |
| 註解關閉後為純成品外觀 | 關閉註解模式後，畫面上不存在編號氣泡或標註元素 |
| 視覺數值對得回基準檔 | 所用色彩與間距逐項對照呼叫端指定且與 app-name 相符的 baseline-path「已統一慣例」或 confirmed-choices 的使用者確認來源 |
| 版面決策說明表存在 | 表格具備三層歸類，且理由欄以業務行為陳述而非視覺詞彙 |
| 畫面覆蓋完整 | 需求摘要涵蓋的畫面皆已產出，無遺漏 |
| 替身外觀有對應樣本頁 | 每個 samplePath 可讀且與 baseline-path 指定 app 相同；對照樣本與 Demo 的標記／CSS 及可見外觀。靜態無法重現者保留限制，不宣稱通過。主要元件無依據或對應錯誤為 Major；單一可定位路徑筆誤為 Minor |
