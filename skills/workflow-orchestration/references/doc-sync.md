# 結案前文件同步

本檔收錄結案前使用者文件同步的盤點、草稿原則、一致性檢查與最終編輯的派生契約、事實核對、收斂處置與報告格式。觸發位置見 `../SKILL.md`「文件同步」。目標是讓受本線影響的使用者文件與改動後的行為一致，並以讀者角度定稿。

## 適用範圍

| 類別 | 判定 | 例 |
| --- | --- | --- |
| 納入 | 以人為讀者的文件：專案根目錄 `README.md`、`docs/` 下手寫文件、使用手冊 | `README.md` |
| 排除：生成檔 | 由腳本或 hook 產生的檔案，依檔頭生成標記或專案 `AGENTS.md` 宣告判定 | `docs/agents.md`、`docs/skills.md` |
| 排除：agent 規則檔 | `instructions.md`、`agents/` 與 `skills/` 下的規則檔與 `SKILL.md`、專案層 `AGENTS.md`、`GLOSSARY.md`，由 Reviewer 審查 | `skills/workflow-orchestration/SKILL.md` |
| 排除：追加式文件 | `docs/adr/`、CHANGELOG。既有條目不改寫，新增由 `adr` skill 與發版流程觸發 | `docs/adr/` 下的 ADR |

受影響文件清單為空時，在盤點來源寫明理由，不執行後續步驟。

## 盤點

| 路徑 | 盤點者與落點 | 草稿者 | 一致性檢查、最終編輯與事實核對的協調者與位置 | 清單為空的寫法 |
| --- | --- | --- | --- | --- |
| `full` | `Architect`。`design.md` §5「使用者文件」子節，欄位為文件路徑、章節標題、影響原因（對應需求編號）、處置（T-code 或「不需要」加理由）；§9 排入草稿 T-code | Developer 執行者依 T-code | 主 Agent。自動推進鏈 Developer 回收之後、Reviewer 派發之前 | 子節寫「無受影響的使用者文件：<理由>」 |
| `light` | 主 Agent 在實作驗收契約新增一列「文件同步」，列出受影響文件絕對路徑與段落標題並標註〔需求 #n〕 | 實作執行者（Claude subagent 或主 Agent 自理） | 主 Agent。回收與升級判定之後、審查判定之前 | 該列寫「不需要：<理由>」 |
| bug 線 | `Maintainer`。fix-plan 與改動計畫的「文件影響」欄 | `Support Engineer` 依計畫 | Claude 端為主 Agent，在 `Support Engineer` 回報並通過 Maintainer 驗收之後。Maintainer 在 Codex 端被叫起時無法派生 Claude subagent，於回報列「文件同步待辦」，由 Claude 端續行 | 欄位寫「無：<理由>」 |

盤點來源為影響範圍盤點報告的「使用者文件引用」節與需求摘要列舉的文件。「使用者文件引用」節以本次改動的術語、檔名、命令與被取代的舊名稱為搜尋詞，列出使用者文件中的命中位置。`Architect` 與 `Maintainer` 不做盤點範圍外的掃描；需求改變使用者可見的行為而沒有盤點來源時，交回協調者補盤點。

## 草稿原則

草稿者更新盤點列出的段落時遵守下列原則。

- 以讀者視角直接陳述改動後的行為。
- 不寫實作過程、內部機制與試錯紀錄。
- 不寫為回應審查或校閱而加的句子，例如說明修正由來或以舊寫法為對照的句子。
- 只動盤點列出的段落；術語或名稱更名時，同一輪更新搜尋詞的全部命中處。

## 一致性檢查

| 項目 | 規格 |
| --- | --- |
| 判定行 | `scripts/Select-DispatchExecutor.ps1 -Type survey`，以輸出的 `dispatchLine` 為判定行 |
| 派生 | 依 `executor-selection` skill「Claude 取證者派生契約」，冷啟動 |
| prompt 必含 | `LineContext`；受影響文件絕對路徑與段落標題；行為來源（本線改動檔案清單與設計或驗收契約對應段落的絕對路徑）；搜尋詞清單；待答問題；輸出落點 `report/<lineSlug>/survey-doc-sync-consistency.md` |
| 待答問題 | (a) 受影響段落中與改動後行為相關的每一句敘述是否相符。(b) 以搜尋詞檢索各文件全文，列出每個命中位置是已更新或殘留。(c) 文件內的交叉引用（章節標題、檔名、命令、表格列數）是否仍成立 |
| 回傳格式 | 每個不符處一列，編號 `DS-<三位數>`，欄位為文件路徑與段落標題、文件原文、對照來源（檔案絕對路徑與行號）與原始摘錄、不符類型（敘述與行為不符、殘留舊名稱、交叉引用失效、其他）。另列搜尋詞與各詞命中數；回報「無不符處」時附搜尋詞零命中的證據 |
| 限制 | 唯讀，除報告檔外不修改任何檔案，不執行 git 寫入命令，不提出修法 |
| 外部事實 | 受影響段落含外部事實（第三方產品或 API 行為、版本號、官方文件連結）時，主 Agent 另以 `-Type factcheck` 呼叫選派入口，依 `fact-check-note` skill 取得 `fact-check-report.md`。不含外部事實時，在 `doc-sync-report.md` 寫「無外部事實」與判斷依據。查證結果由主 Agent 依下表判定，流程不經 `apply-fact-check` |

主 Agent 對每個 `DS` 項判定處置，取證者不修改文件。

| 判定 | 條件 | 處置 |
| --- | --- | --- |
| 文件敘述有誤 | 文件與實際行為不符，且行為符合需求與設計 | 主 Agent 修正文件（小型修改例外內自理，超過門檻以 `-Type edit` 選派），修正處以搜尋詞 `rg` 覆核 |
| 系統行為有誤 | 行為與需求或設計不符 | 退回實作者，修正後對受影響段落重跑一致性檢查，不修文件遷就行為 |
| 誤報 | 取證者的對照來源有誤 | 附反證位置，記於 `doc-sync-report.md` |
| 需求意圖不明 | 行為對錯取決於需求摘要未涵蓋的業務語意 | 套用升級兩道篩，命中時全停 |

`fact-check-report.md` 的 `❌`（附官方來源）依其「正確事實」修正；`⚠️` 由主 Agent 判定是否影響文件敘述，影響而無法判定者套用升級兩道篩。

## 最終編輯

事實修正全部完成後執行。最終編輯是未參與寫作的第二讀者，以讀者角度定稿。

| 項目 | 規格 |
| --- | --- |
| 判定行 | `scripts/Select-DispatchExecutor.ps1 -Type edit -E false -T false`，以輸出的 `dispatchLine` 為判定行。`E` 固定為否，因為定稿時要刪除或潤飾的句子無法於派工前逐一列出 |
| 前置 | 受影響文件快照存入 `<work-root>/.local/ai-sessions/scratch/doc-sync/<序號>/`。目標文件與 `git status --porcelain` 的他人項目有交集時不派生，停止並回報 |
| 派生 | `subagent_type` 為 `general-purpose`，`model` 取自 `executor.model`，冷啟動。不切換 Persona |
| 規則來源 | `~/.ai-agents/agents/claude/editor.md` 全文 in-context 傳入，宣告適用「改寫情境」與「文件同步定稿模式」；載入 `doc-editing` 與 `check-markdown` skill |
| prompt 必含 | `LineContext`；受影響文件絕對路徑與段落標題；快照路徑（只讀對照）；需求摘要路徑與 `design.md` §1 或驗收契約，供判斷讀者需要什麼；一致性檢查與事實查證報告路徑，只用於辨識為回應校閱而寫的句子與已定案的事實；寫入範圍；報告落點 |
| 寫入範圍 | 受影響文件與 `report/<lineSlug>/doc-edit-report.md`，其餘一律不寫，不執行 git 寫入命令 |
| 全文潤飾條件 | 原則只處理受影響段落。符合下列任一項才可全文潤飾，並於報告寫明條件編號、範圍與理由。(F1) 本線改變的術語或名稱在全文多處出現。(F2) 受影響段落需要調整段落結構（合併、拆分、重排）。(F3) 全文對同一概念使用兩種以上稱呼且明顯不一致 |
| 不改事實 | 版本號、數字、命令、路徑、檔名、識別字與行為敘述的語意維持原狀。認為事實有誤時不改，列入報告「疑似事實問題」交主 Agent |
| 刪除授權 | 只限檢查項目 1 與 2 的類別，每筆登記於報告「刪除清單」。其餘內容只在報告提出建議，不刪除 |

| # | 檢查項目 | 判準 |
| --- | --- | --- |
| 1 | 讀者不需要的細節 | 實作過程、內部機制、試錯紀錄。刪除後讀者的使用、設定與判斷不受影響才刪 |
| 2 | 為回應校閱而寫的句子 | 只為說明修正由來或以舊寫法為對照的句子，改為直接陳述事實，不保留修正痕跡 |
| 3 | 用語與語句 | 台灣用語、語句通順，遵守 `editor.md` 的輸出禁忌 |
| 4 | 術語一致 | 全文同一概念使用同一名稱，本線新增或更名的術語以最終名稱為準 |
| 5 | 排版 | 依 `check-markdown` |
| 6 | 全文一致性審視 | 受影響段落以外的不一致列入報告「全文一致性觀察」，符合全文潤飾條件才修改 |

## 事實核對

最終編輯回報後，主 Agent 依序執行。

1. 取得快照與現檔的差異（`git diff --no-index` 或等效比較），逐 hunk 歸類為措辭、刪除、結構、術語統一。
2. 比對事實 token。抽取反引號內容、版本號與數字、命令、路徑與檔名、表格儲存格值。現檔缺少的 token 必須出現在報告刪除清單且屬檢查項目 1；現檔新增的 token 必須存在於快照、取證報告或設計文件，否則視為新增事實。
3. 比對行為敘述。被改寫的行為敘述逐句與快照核對動詞、對象、條件與否定。token 比對偵測不到語意改寫，本步驟以閱讀 diff 為準；diff 量大到會持續留在主 Agent context 時，可交覆核取證助手。
4. 以取證報告的搜尋詞對最終文件執行 `rg`，殘留數為 0。
5. 對最終文件執行 `check-markdown` 的檢查。
6. 全文潤飾啟用時，核對條件編號成立，且 diff 範圍與報告宣告的範圍相符。

未通過項退回最終編輯（同一契約，`round` 加 1），或在小型修改例外內由主 Agent 還原該 hunk。

## 收斂與處置

- 沿用 `../SKILL.md`「共同收斂契約」。`area-key` 為文件路徑加最近標題，`problem-key` 為 `DS-<三位數>`（一致性檢查）與 `FC-<三位數>`（事實核對），`max-rounds` 為 6。
- 審查退回後的修正若改變行為、術語或檔名，對受影響段落重跑一致性檢查、最終編輯與事實核對。
- 最終編輯只改盤點列出的文件；`full` 線的這些路徑落在 Developer 結案報告「Phase 對照」節內，Phase commit 回收時一併暫存。
- 同線同時只執行一次文件同步，不平行編輯同一文件；退回後的下一輪以新快照為基準，快照序號遞增。
- 清單所列文件不存在或無法讀取時，停止並回報協調者，不自行改清單。
- 取證者或最終編輯遭服務端拒絕時，停止並回報使用者。外部事實無法查證時列為未解決項目，文件同步不算完成。

## 報告

| 檔案 | 作者 | 章節 |
| --- | --- | --- |
| `report/<lineSlug>/doc-sync-report.md` | 主 Agent | `## 受影響文件清單`（來源、文件、段落、影響原因、T-code）；`## 一致性檢查`（取證報告路徑、搜尋詞與命中數、`DS` 判定表、外部事實處置）；`## 最終編輯`（判定行、編輯報告路徑、輪數、全文潤飾是否啟用）；`## 事實核對`（六步結果、未通過項與處置）；`## 結論`（通過或未通過、未解決項目） |
| `report/<lineSlug>/doc-edit-report.md` | 最終編輯 subagent | `## 改動摘要`（文件、位置、改動類型、一句話說明）；`## 刪除清單`（原文、類別、理由）；`## 全文潤飾`（未啟用，或條件編號、範圍、理由）；`## 全文一致性觀察`；`## 疑似事實問題`；`## 寫入後自檢`（沒有命中寫「無」） |
| `report/<lineSlug>/survey-doc-sync-consistency.md` | Sonnet 取證者 | 依「一致性檢查」回傳格式 |

清單為空時不建立三份報告，Analyst 與結案報告引用盤點來源的「無」與理由。取證報告缺來源位置或原始摘錄、編輯報告缺刪除清單或與實際 diff 不符時，退回該執行者。
