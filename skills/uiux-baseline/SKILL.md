# 專案樣式基準抽取

此 Skill 掃描專案既有樣式，產出一份供 AI 與使用者共同閱讀的樣式基準檔。基準檔記錄的是專案的客觀統計事實，不是建議值，用途為讓後續的畫面規劃與 Demo 產製有可引用的視覺依據，不必每次重新想像。

基準檔含兩類內容。一類是色彩、間距、字級、圓角的原子值，用於還原局部觀感。另一類是可整段複用的具名版型模式，例如查詢條件列與資料表格，用於還原版型慣例。只有原子值時，後續產出的畫面仍會偏離專案既有版型，因此兩類缺一不可。

專案既有樣式本身可能不一致。此 Skill 的職責是把不一致暴露出來交由使用者決定，不是替使用者選定其中一種寫進基準。

## 啟動條件

符合任一條件時套用：

- 使用者要求建立或更新專案的樣式基準。
- 使用者要求盤點專案既有的視覺慣例。
- `uiux` skill 或 `UI Demo` sub-agent 需要引用基準檔，而目標路徑尚無檔案。

## 執行流程

### Phase 1：掃描範圍判定

1. 依主規則判定 `work-root`。
2. 辨識前端來源目錄，納入下列副檔名的檔案：
   - 標記語言：`.html`、`.cshtml`、`.aspx`、`.master`、`.razor`、`.vue`、`.jsx`、`.tsx`
   - 樣式表：`.css`、`.scss`、`.less`
3. 一併納入主題設定檔，包含 Tailwind 設定檔、CSS 變數定義檔、Bootstrap 或其他框架的覆寫檔。
4. 排除 `bin/`、`obj/`、`dist/`、`out/`、`build/`、`node_modules/`、`.local/`。
5. 單一 `work-root` 下存在多個前端 app 時，逐一產出獨立基準檔，以檔名後綴區分。

### Phase 2：來源分層

抽取前先將掃描到的樣式來源分為三層。層級決定該來源的值在後續判定中的角色。

| 層級 | 範圍 | 在判定中的角色 |
| --- | --- | --- |
| 權威層 | 主要版型檔載入的共用 CSS、CSS 變數定義檔、框架主題設定檔 | 直接列為專案慣例，不參與門檻投票 |
| 佐證層 | 個別檢視或元件檔內的 `<style>` 區塊 | 參與門檻投票，並用於判定權威層是否被普遍覆寫 |
| 雜訊層 | 標記上的行內 `style` 屬性 | 不進入值的計數池，僅記錄總量與覆寫熱點 |

權威層的判定方式為找出被最多檢視引用的版型檔，讀取其載入的樣式表清單。專案無明確版型檔時，改以被最多檢視直接引用的樣式表為權威層。

行內樣式不進計數池的理由是，既有專案的行內樣式宣告數常達共用 CSS 的數十倍。兩者混入同一池時任何主導值都無法成立，判定結果會退化為「全部未統一」，基準檔因此失去可引用的內容。

### Phase 3：原子值抽取

依下列四個面向抽取實際使用值。每個值記錄出現次數與至少一處代表檔案位置（含行號）。

| 面向 | 抽取內容 |
| --- | --- |
| 色彩 | 文字色、背景色、邊框色、主要動作色、狀態色（成功、警示、錯誤、停用） |
| 間距與尺寸 | 內距、外距、元件高度、容器最大寬度、斷點值 |
| 字級與字重 | 各層級標題、內文、輔助文字的字級與字重 |
| 圓角與陰影 | 圓角半徑、陰影層級 |

抽取的是**實際出現在程式碼中的值**，不是框架預設值。專案透過 CSS 變數或 Tailwind 設定集中定義時，以該定義為準並註明來源檔案。

統計單位為**用途類**，定義為「元件 × 屬性」的組合，例如「主要按鈕背景色」「表格表頭背景色」「卡片內距」「頁面標題字級」。禁止退化成跨全專案的單一屬性池，例如把所有 `background-color` 宣告合併計數。屬性層級的統計在多頁面專案必然無主導值，得到的結論無法引用。

### Phase 4：複合樣式模式抽取

原子值只能還原局部觀感，無法還原專案的版型慣例。本階段抽取可整段複用的具名模式，例如查詢條件列、資料表格、彈窗、頁首工具列、表單欄位群。

抽取起點為**權威層樣式表中的具名 class 與 id 選擇器**，不是 HTML 標籤。流程如下：

1. 列出權威層樣式表的具名選擇器，排除框架原生選擇器與純工具類。
2. 對每個選擇器統計引用它的檢視檔數量。
3. 取引用數前段的選擇器，依語意歸併為模式。同一模式常由數個選擇器組成，例如表頭與資料區各一個。
4. 從引用該模式的檢視中取一個結構完整的實例，作為 HTML 骨架的來源。

以標籤出現次數統計元件是無效作法。「按鈕標記出現 2,962 次」不構成可引用的資訊，具名 class 與其對應的 CSS 規則才是。

### Phase 5：一致性判定

權威層的值直接列入「已統一慣例」，不參與門檻判定。專案把某個值寫進共用樣式表，本身即為慣例的表態。

佐證層的值依下列門檻判定：

| 判定結果 | 條件 |
| --- | --- |
| 已統一 | 存在主導值（佔該用途類出現次數 70% 以上），且其餘任一值佔比低於 20% |
| 待決策 | 不符合上述條件 |
| 待決策（樣本不足） | 該用途類總樣本數低於 3 |

判定為待決策時，列出全部候選值、各自出現次數與代表位置，不擇一。

佐證層的值與權威層衝突，且該值在佐證層佔比過半時，列為待決策項並註明衝突的權威層來源。

### Phase 6：產出

寫入 `<work-root>/.local/ai-sessions/baselines/ui-style-baseline.md`。多個前端 app 時，檔名為 `ui-style-baseline.<app-name>.md`。

檔案的一級章節固定為下列六節，順序不得調換：

1. `## 掃描範圍`
2. `## 已統一慣例`
3. `## 常用模式範例`
4. `## 待決策項`
5. `## 未偵測到的面向`
6. `## 引用方式`

「掃描範圍」需記錄產生時間、掃描的目錄與檔案數、排除的目錄，以及 Phase 2 判定出的三層來源各自涵蓋哪些檔案，供後續判斷基準是否已過期。

「已統一慣例」下的二級章節固定為四節，對應 Phase 3 的四個面向，順序為「色彩」「間距與尺寸」「字級與字重」「圓角與陰影」。**本節只放通過判定的值**。未達門檻的值一律歸入「待決策項」，不得以候選值預覽的形式重複列於本節。

「常用模式範例」下每個模式為一個二級章節，含下列五項：

| 項目 | 內容 |
| --- | --- |
| 用途 | 該模式解決的畫面情境 |
| 來源 | 權威層樣式表的檔案路徑與行號範圍 |
| 引用 | 引用該模式的檢視檔數量，與一處代表位置 |
| HTML 骨架 | 從代表檢視取出的結構，保留 class 與巢狀關係，移除業務資料 |
| CSS 規則 | 原樣引用來源樣式表的規則 |

HTML 骨架與 CSS 規則皆為專案既有程式碼的引用。除縮排外不得改寫內容，不得補上來源中不存在的屬性，不得為了看起來完整而合併多處來源。

「待決策項」的每一列須含下列五欄：

| 欄位 | 內容 |
| --- | --- |
| 用途類 | 該值的使用情境 |
| 候選值 | 全部出現過的值 |
| 出現次數 | 各候選值各自的次數 |
| 代表位置 | 各候選值的檔案路徑與行號 |
| 未自動擇一的原因 | 一句話說明未達門檻的方式（如「兩值佔比接近」「樣本不足」） |

「引用方式」需說明引用方為 `uiux` skill 與 `UI Demo` sub-agent，兩者僅讀不寫，「常用模式範例」的骨架可整段複用，以及待決策項在被引用時須先取得使用者確認。

### Phase 7：回報

回報下列內容，並將待決策清單交回呼叫端：

- 基準檔的完整路徑。
- 已統一項數、模式數與待決策項數。
- 待決策清單，供呼叫端決定是否需先請使用者確認。

## 約束

- 不修改任何專案樣式檔。此 Skill 唯一可寫入的位置為 `<work-root>/.local/ai-sessions/baselines/`。
- 不讀取 `.env` 與建置輸出目錄。
- 不對專案樣式的優劣下評價，只陳述統計事實。基準檔中不出現「建議改為」「應改用」等措辭。
- 某面向掃描不到資料時，列入「未偵測到的面向」章節，不以框架預設值或通用值填補。
- 不以標籤出現次數代替複合樣式模式的抽取。統計不到具名模式時，列入「未偵測到的面向」，不以標籤計數充數。
- 不替使用者選定待決策項的答案。
