# ADR-0039：協調 Session 轉述的使用者決定視同接收端當輪授權

## Context

使用者同時開多條線時，主要在一個協調 Session 對話，再由它把決定傳給各線的 Session。原本的規則只承認使用者在執行端當輪的直接回覆，其他 Session 送來的訊息一律不算授權，使用者因此要逐一切換到各 Session 重複回答同一個決定。使用者的回覆常是「好」「照建議」這類短句，接收端無法從 transcript 可靠查證它對應哪個問題。

## Decision

接收端只以平台信封 `<cross-session-message>` 的 `from` Session id 判定發送端，`from` 等於接收端的 `startedBy` 時，發送端即為協調 Session，標題與名稱不參與判定。協調 Session 轉述的使用者決定同時符合下列條件時，視同使用者在接收端當輪授權，接收端不另查 transcript。

- 動作屬可轉述範圍，限能復原的本機動作。寫入需求摘要須先完成覆寫前備份；範圍取捨；`feature/<lineSlug>` 的本機 commit；線分支 rebase 須先建備份分支，遇到衝突就停下，解衝突需要新的當輪授權。
- 轉述附上三要素，即使用者原話、使用者回應的問題原文，以及被確認內容的全文或可逐項比對的版本。接收端與自己的草稿逐項比對，完全一致才執行。
- 寫入需求摘要、線分支本機 commit 與 rebase 每次轉述只涵蓋一次動作。範圍取捨另可事先列明範圍，讓同一個已定案的決定套用到同線後續多次動作，被確認內容須寫出決定本身、所屬線的 `lineSlug` 與涵蓋邊界，例如「`doc-placement` 剩下的全部審查改由 Sonnet 做同家族審查，含各循環後續輪次」。只寫範圍、未寫決定者等同決策權交付，不算授權。列明範圍的轉述不跨線套用，在該線結案時失效，使用者可在協調 Session 撤銷或改變。範圍外或無法判定是否涵蓋的動作視為未授權。接收端每次執行前都輸出判定行。

push、force push、刪除、安裝套件或下載相依性、發佈、advisor 授權、整合分支落地與合併、打標籤不可轉述，使用者須在執行端當輪授權。協調 Session 以外的 Session 轉來的授權一律不算數；使用者手動開啟、沒有 `startedBy` 的 Session 沒有協調 Session。

排除的方案如下。在 `machine.json` 登記協調 Session id，會因為每個專案各有協調 Session 且會更換而需要不斷修改本機設定。接收端查 transcript 驗證，無法可靠對應短句回覆。比對發送端標題，標題可以被任何 Session 設定。限定每則轉述只涵蓋一次動作，會讓「同一線剩下的審查都改給某執行者」這類決定在每一輪都要重新詢問使用者。讓所有可轉述動作都能列明範圍，會使寫入需求摘要或 commit 在使用者沒看過內容時就執行，因此只開放範圍取捨。

## Consequences

使用者在協調 Session 回答一次，即可讓它開出的各線繼續推進，列明範圍的決定不必在每一輪重複確認。要讓某 Session 接受轉述，必須由協調 Session 開出它。不可逆或對外的動作仍需使用者到執行端回覆。列明範圍的寫法若含糊或缺少定案決定，接收端會停下來確認，範圍描述的明確度由協調 Session 負責。
